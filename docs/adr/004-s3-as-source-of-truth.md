# ADR-004: サーバーサイドDB不使用・S3をシングルソースオブトゥルースとする

**ステータス:** Accepted
**決定日:** 2026-02
**関連:** `docs/design/architecture.md §solidrop-api-server`, `README.md §判断5`

---

## Context

ファイルメタデータ（パス・サイズ・ハッシュ・最終更新日時）の管理方法として、以下の選択肢があった:

**案A: サーバーサイドDB（DynamoDB / PostgreSQL 等）**
メタデータをDBに保存し、高速なクエリを実現する。

**案B: S3をソースオブトゥルースとする**
S3の `ListObjects` API + オブジェクトメタデータタグを使用する。DBは持たない。

---

## Decision

**サーバーサイドDBは設けない。ファイルメタデータはS3オブジェクトのメタデータタグとして保存する。**

S3オブジェクトに付与するタグ:
- `x-amz-meta-content-hash`: 平文のSHA-256ハッシュ
- `x-amz-meta-original-size`: 暗号化前のファイルサイズ（bytes）
- `x-amz-meta-original-name`: 元のファイル名

ファイル一覧取得は `S3::ListObjectsV2` + タグ取得で実装する。

---

## Rationale

**なぜDBが不要か:**

個人ユーザー1人が管理するファイル数は、S3の `ListObjects` API（最大1000件/ページ）で十分に対応できる規模である。
ファイル数が数千件になっても、月間数十回のリスト取得操作では S3 API のコスト・レイテンシは問題にならない。

複雑なクエリ（全文検索・集計等）は現在の要件に存在しない。

**DBを追加した場合のコスト（却下理由）:**

| コスト | 内容 |
|---|---|
| インフラコスト | DynamoDB: 月額 $1-5 程度の追加コスト |
| 運用コスト | DBとS3の二重管理。整合性維持ロジックが必要 |
| 障害リスク | DBとS3が非同期になった場合の不整合 |
| 学習コスト | DynamoDB/ORM の学習が必要 |

**S3がソースオブトゥルースであることの利点:**

- S3にオブジェクトが存在することが真実であり、DBとの不整合が原理的に起きない
- APIサーバーがステートレスになる（再起動・障害復旧が容易）
- DynamoDB/Fargate 等の追加AWSサービスが不要。初年度コストを $0.4/月 に抑えられる

---

## Consequences

**正の結果:**
- サーバーが完全にステートレス（スケールアウト・再起動が容易）
- S3 = 唯一の真実。DBとS3の不整合が構造的に発生しない
- インフラがシンプル（S3 + VPSのみ）
- クライアント側ローカルSQLiteは引き続き使用（キャッシュ状態管理のみ）

**負の結果:**
- ファイル一覧取得で毎回 S3 API を叩く（キャッシュなし）
  → 個人利用レベルのリクエスト頻度では問題なし。必要なら将来的にキャッシュ追加可能
- 高度なメタデータ検索（タグ検索・日付範囲フィルタ等）は現状 S3 API の制約内でしか行えない
  → Phase 1 の要件には存在しない。必要になれば Phase 2 で再検討（DEF-3）
- `ListObjectsV2` は結果数が多い場合にページネーションが必要
  → ページネーション対応は API で実装済み（`next_token` フィールド）
