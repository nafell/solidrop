# ADR-005: iPadローカルストレージをLRUキャッシュとして扱い、承認制で退避する

**ステータス:** Accepted
**決定日:** 2026-02
**関連:** `docs/design/architecture.md §Data Flow: Cache Eviction`, `README.md §12`

---

## Context

iPadの内蔵ストレージは128GB。.clip ファイルは中央値30MB・最大55MB。
3年間の蓄積で15〜30GBに達する見込みであり、ストレージ管理が必要になる。

ファイル管理戦略の選択肢として以下が検討された:

**案A: 手動削除**
ユーザーが不要なファイルを都度手動でS3に逃がし、ローカルから削除する。

**案B: 完全自動退避**
LRU順に自動的にクラウドに退避し、ローカルから削除する。

**案C: 承認制LRU退避（採用案）**
LRUで退避候補を算出してユーザーに提示し、承認後に退避する。

---

## Decision

**iPadのローカルストレージをS3をバッキングストアとするLRUキャッシュとして設計する。退避はユーザー承認制とする。**

パラメータ:
- ローカル保持上限: デフォルト 60GB（ユーザー設定可）
- 退避選定基準: `last_used` 昇順（最も古く使われていないファイルから候補に挙げる）
- 退避フロー: 候補提示 → ユーザー承認 → S3上のファイル存在確認（content_hash照合）→ ローカル削除

---

## Rationale

**なぜLRUキャッシュ戦略か:**

コンピュータアーキテクチャにおけるCPUキャッシュ・ページング等の場面で実績があるLRU戦略を適用した。
「最近使ったファイルは近いうちにまた使う」という局所参照性の原理はお絵かきワークフローにも適合する。
（進行中の作品ファイルは頻繁にアクセスされ、完成済みの古い作品は閲覧頻度が下がる）

**なぜ完全自動退避（案B）ではなく承認制（案C）か:**

本システムの最優先目的は「お絵かきUXの向上」である。

完全自動退避の最大のリスクは「今日描こうとしていたファイルが消えていた」という体験である。
たとえLRUアルゴリズムが「最も古い」と判断しても、ユーザーはその日の朝に描くつもりだったかもしれない。
この失敗体験はシステムへの信頼を損ない、目的（お絵かきUX向上）を達成できなくなる。

承認制にすることで:
- ユーザーが退避前に「このファイルは削除していいか」を確認できる
- 誤退避が発生しない（正確にはユーザーが意図的に承認した場合のみ退避）
- ストレージ上限に近づいていることを通知としてユーザーに伝えられる

自動退避はPhase 2以降で、承認制の使用感・実際のアクセスパターンを見てから検討する（DEF-4）。

**なぜ手動削除（案A）ではないか:**

毎回の手動操作はユーザーの負担になる。
LRU候補の自動算出という「仕事の9割をシステムが行い、最終決定だけ人間が行う」設計が最もバランスが良い。

---

## Consequences

**正の結果:**
- 「意図しないファイル喪失」が発生しない（ユーザーが明示的に承認するまでローカルファイルは安全）
- LRU計算はサーバーサイドで実施するため、クライアント（Flutter）の処理を軽量に保てる
- 退避候補の通知がストレージ管理の意識づけになる

**負の結果:**
- ストレージが上限を超えた際、ユーザーが承認しない限り退避が行われない
  → 個人ツールとして、強制退避よりユーザー意思尊重を優先。許容可能。
- LRUの `last_used` 更新はアプリ内のファイルピッカーからしか追跡できない（iOSサンドボックス制約）
  → クリスタ内で開いたタイミングは追跡不能。これはiOS制約の範囲内で許容。File Provider Extension（Phase 3）で改善予定。
