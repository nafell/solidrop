# ADR-006: API層にValkey永続インデックスを導入し、S3メタデータ参照を最適化する

**ステータス:** Accepted
**決定日:** 2026-03
**関連:** `docs/design/architecture.md §solidrop-api-server`, `README.md §11`
**Supersedes:** [ADR-004](004-s3-as-source-of-truth.md)

---

## Context

ADR-004では「サーバーサイドDBなし」を採用したが、以下の課題が明確になった:

- `ListObjectsV2` だけでは必要なメタデータを十分に返せず、追加API呼び出しが増える
- 一覧取得・検索要件の拡張に対してAPIレイテンシが不安定になる
- APIの責務として、S3オブジェクトを即時に扱える索引を持つ方が実装が明確

また、将来API実行基盤をCloudflare Workersへ移行する可能性もあるが、現状はXServer VPS (Ubuntu) 上のDocker運用が前提である。

## Decision

**API層にValkey（Redis互換）を導入し、ファイルメタデータの永続インデックスとして利用する。**

- 配置: VPS上でAPIサーバーと同居（Docker Compose）
- 永続化: AOF有効
- データモデル: `path` を主キーにメタデータを保持
- 役割分担:
  - **S3:** 暗号化ファイル本体の保管（最終的な実体）
  - **Valkey:** 一覧・検索・運用処理のためのメタデータインデックス

整合性方針:
- 書き込みは `S3成功 → Valkey更新` の順
- 途中失敗時は再試行キューまたは再同期ジョブで回復
- 定期再同期（S3→Valkey）を用意して自己修復可能にする

## Rationale

**なぜVPS同居か:**
- 現行運用（XServer VPS）との整合が高く、導入コストが最小
- ネットワークレイテンシが小さく、障害点を増やしにくい

**なぜValkeyか:**
- 個人プロジェクトで導入・運用が容易
- キー設計がシンプルで、一覧・順位付け・TTLなど拡張余地がある
- 将来クラウドマネージドに移行しやすい（Redis互換）

**なぜドキュメント系NoSQLを選ばないか:**
- 本件のアクセスパターンはキー中心で、Valkeyの方が設計が直接的
- 個人運用での初期学習・保守コストを抑えられる

## Consequences

**正の結果:**
- 一覧APIの応答が安定し、N+1的なS3問い合わせを減らせる
- API層でメタデータ責務が明確になる
- 将来の検索要件に対応しやすい

**負の結果:**
- S3とValkeyの二重管理となり、整合性回復ロジックが必要
- 運用対象サービスが1つ増える
- Workers移行時にはValkey接続性・配置を別途検討する必要がある
